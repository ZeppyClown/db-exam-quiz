1 · SQL queries: patterns and traps

1.1 How to attack any SQL question

  1. Underline the output columns the question asks for. That's your SELECT.
  2. Find the path of tables that connects those columns to the conditions. Every table on the path goes in FROM/JOIN, joined on its key = foreign key.
  3. Row conditions (category = 'coffee', date = …) go in WHERE.
  4. “per / for each / total / count” → GROUP BY. A condition on a count or total → HAVING.
  5. Watch for keywords that change the shape: “all”, “never”, “only”, “both”, “the most”, “ties”, “no JOIN allowed”. Each has a fixed pattern, covered below.
  6. Ask yourself: can the joins create duplicate rows? If so, use DISTINCT or COUNT(DISTINCT …).

1.2 WHERE vs HAVING

WHERE filters individual rows before grouping, so it can't contain aggregates. HAVING filters whole groups after grouping, so it's where aggregates go.

-- Packages over $500, and for each destination with 3+ such packages, the count
SELECT DID, COUNT(*) AS n
FROM PACKAGE
WHERE price > 500          -- row filter: looks at each package
GROUP BY DID
HAVING COUNT(*) >= 3;      -- group filter: looks at each destination's count
MistakeWHERE COUNT(*) >= 3 is an error. Also, every non-aggregated column in SELECT must appear in GROUP BY. Group by the id, not just the name, because two customers can share a name.

1.3 “For ALL” (relational division) → double NOT EXISTS

Example: students who took every course. SQL has no “for all”, so you turn it around: a student qualifies if there is no course they didn't take.

SELECT S.name
FROM Student S
WHERE NOT EXISTS (                 -- there is no course...
    SELECT * FROM Course C
    WHERE NOT EXISTS (             -- ...that this student did not take
        SELECT * FROM Took T
        WHERE T.sid = S.sid
          AND T.cid = C.cid));
Why it worksFor each student S, the middle query lists the courses S is missing. If that list is empty (NOT EXISTS is true), S took them all.

Counting alternative (fine if Took.cid is a foreign key to Course):

SELECT sid FROM Took
GROUP BY sid
HAVING COUNT(DISTINCT cid) = (SELECT COUNT(*) FROM Course);
Exam variant (2024-25 S2)“bought all 'car' products in a single order.” Now the thing that must cover everything is an order, so wrap the double NOT EXISTS inside EXISTS (SELECT * FROM [ORDER] O WHERE O.customerid = C.customerid AND NOT EXISTS (...car product not in O...)).

1.4 “Never” / “not” → NOT EXISTS

-- customers who never bought a Singapore-made product
SELECT C.customername FROM CUSTOMER C
WHERE NOT EXISTS (
    SELECT * FROM [ORDER] O
    JOIN ORDER_ITEM OI ON OI.orderid = O.orderid
    JOIN PRODUCT P     ON P.productid = OI.productid
    JOIN PRODUCER PR   ON PR.producerid = P.producerid
    WHERE O.customerid = C.customerid AND PR.country = 'Singapore');
Mistake 1: NOT IN with NULLsWHERE sid NOT IN (SELECT sid FROM TxnLog) returns nothing at all if any TxnLog.sid is NULL, because x <> NULL is UNKNOWN. NOT EXISTS doesn't have this problem, so default to it.
Mistake 2: “<>” in a join is not negationJOIN ... ON T.card_to <> H.cardid finds rows where some transfer went elsewhere. It does not mean “never received a transfer”.

1.5 “Both X and Y”

WHERE looks at one row at a time, and one row can't have two categories. So WHERE category='coffee' AND category='tea' is always empty. Correct versions:

-- (a) two EXISTS / IN
SELECT C.name FROM Customer C
WHERE EXISTS (SELECT * FROM Orders O WHERE O.cid = C.cid AND O.category = 'coffee')
  AND EXISTS (SELECT * FROM Orders O WHERE O.cid = C.cid AND O.category = 'tea');

-- (b) count distinct
SELECT cid FROM Orders
WHERE category IN ('coffee', 'tea')
GROUP BY cid
HAVING COUNT(DISTINCT category) = 2;

... IN (coffee) OR IN (tea) means either, not both.

1.6 “Only X”

Customers who bought only coffee = bought coffee and not bought anything else:

SELECT DISTINCT cid FROM Orders O
WHERE category = 'coffee'
  AND NOT EXISTS (SELECT * FROM Orders O2 WHERE O2.cid = O.cid AND O2.category <> 'coffee');

1.7 “The most / highest” with ties

Examiners write “if there's a tie, return all of them”. TOP 1 loses marks. Two correct ways:

-- (a) compare with MAX
SELECT name, age FROM STUDENT
WHERE age = (SELECT MIN(age) FROM STUDENT);      -- all the youngest

-- (b) >= ALL, when the "score" is an aggregate
SELECT A.aID
FROM TOUR_PACKAGE A
GROUP BY A.aID
HAVING COUNT(*) >= ALL (SELECT COUNT(*) FROM TOUR_PACKAGE GROUP BY aID);
Mistake>= ALL returns nothing if the subquery contains a NULL, the same trap as NOT IN. = (SELECT MAX…) is safe because MAX ignores NULLs.

1.8 “The most” per group (group-wise max)

For each category, the product(s) with the highest total sales. Same as 1.7, but the subquery is correlated on the category:

SELECT P.category, P.pname, P.price
FROM PRODUCT P
JOIN ORDER_ITEM OI ON OI.productid = P.productid
GROUP BY P.productid, P.category, P.pname, P.price
HAVING SUM(OI.price * OI.quantity) >= ALL (
    SELECT SUM(OI2.price * OI2.quantity)
    FROM PRODUCT P2 JOIN ORDER_ITEM OI2 ON OI2.productid = P2.productid
    WHERE P2.category = P.category            -- same category only
    GROUP BY P2.productid);

1.9 Pairs: “X and Y who were together”

Join the table with itself using two aliases. Match on whatever “together” means. Use < so you don't get (Ann, Ann), or both (Ann, Bob) and (Bob, Ann).

-- pairs of products bought in the same order, with number of distinct customers
SELECT A.productid, B.productid, COUNT(DISTINCT O.customerid) AS n
FROM ORDER_ITEM A
JOIN ORDER_ITEM B ON B.orderid = A.orderid AND A.productid < B.productid
JOIN [ORDER] O    ON O.orderid = A.orderid
GROUP BY A.productid, B.productid;

1.10 “Without using JOIN”

One paper banned the JOIN keyword. Nest IN or EXISTS subqueries instead:

SELECT name FROM STUDENT
WHERE age >= 21
  AND sID IN (SELECT sID FROM MEMBERSHIP
              WHERE yearJoin >= 2020
              GROUP BY sID HAVING COUNT(*) > 4);

1.11 Counting zero: LEFT JOIN

An inner join drops rows with no match, so a student with 0 activities simply disappears. To show 0, use LEFT JOIN and count a column from the right-hand table:

SELECT S.name, COUNT(A.date) AS n         -- COUNT(column) skips NULLs → 0
FROM STUDENT S
LEFT JOIN MEMBERSHIP M ON M.sID = S.sID
LEFT JOIN ACTIVITY A   ON A.cID = M.cID
GROUP BY S.sID, S.name;
MistakeCOUNT(*) here gives 1 for a student with no activities, because the LEFT JOIN row (Ann, NULL, NULL) is still a row.

1.13 Other syntax that comes up

  • Dates: '2025-01-03', YEAR(d) = 2022, MONTH(d), d BETWEEN '2024-12-01' AND '2024-12-31', FORMAT(d, 'yyyy-MM'), GETDATE().
  • LIKE: name LIKE 'J%' (starts with J), LIKE '%Fashion%' (contains).
  • UNION to list two kinds of people together, with a constant label column:
    SELECT TID AS ID, Tname AS Name, 'Trainer' AS Role FROM TRAINER WHERE Tname LIKE 'Je%' UNION SELECT SID, Sname, 'Student' FROM STUDENT WHERE Sname LIKE 'Je%';
  • Conditional count: SUM(CASE WHEN gender = 'M' THEN 1 ELSE 0 END) AS males.
  • Reserved words as table names: [ORDER], [USER].
  • Some papers say “if a query cannot be constructed, explain why”. For example, a trainer can only be linked to students through SIGNUP, and if a needed attribute doesn't exist, say so.

2 · Predicting SQL output (tracing)

A whole 25-mark question in 2025-26 S2 was “which output is correct?”. The method: never trace in your head. Write out the joined rows.

  1. Write the FROM tables as a list of all row combinations that pass the WHERE/ON condition.
  2. Cross out rows that fail any condition. Remember NULL comparisons fail.
  3. Group them, and count or sum each group.
  4. Apply HAVING, then SELECT only the listed columns. Columns you grouped by but didn't select don't appear.

The distractors they use

  • Undercounting a row that matches through both sides of an OR.
  • Forgetting that a shared row (one card held by two students) counts once for each holder.
  • HAVING COUNT(*) >= ALL (...) with ties returns several rows.

3 · CREATE TABLE, INSERT, constraints

3.1 CREATE TABLE: everything they look for

CREATE TABLE BOOKING (
  PID          INT          NOT NULL,                 -- 4-digit id → INT
  email        VARCHAR(100) NOT NULL,
  booking_date DATE         NOT NULL,
  num_guests   INT          NOT NULL CHECK (num_guests > 0),      -- attribute CHECK
  status       VARCHAR(10)  NOT NULL DEFAULT 'pending'
               CHECK (status IN ('pending', 'confirmed', 'cancelled')),
  PRIMARY KEY (PID, email, booking_date),                          -- composite key
  FOREIGN KEY (PID)   REFERENCES PACKAGE(PID),
  FOREIGN KEY (email) REFERENCES [USER](email)
      ON DELETE CASCADE                                            -- optional policy
);

Types: ids → INT · names/text → VARCHAR(n) · money → DECIMAL(10,2) · dates → DATE · times → TIME.

FK policies: default = reject the change · ON DELETE CASCADE = delete the children too · ON DELETE SET NULL.

3.2 INSERT: parents first

A foreign key must point to a row that already exists, so insert in dependency order:

INSERT INTO [USER] (email, name, signup_date) VALUES ('alice@gmail.com', 'Alice', '2025-06-21');
INSERT INTO DESTINATION (DID, dname, country, description)
       VALUES (1001, 'Milan', 'Italy', 'Fashion capital with rich history...');
INSERT INTO PACKAGE (PID, pname, price, duration, DID) VALUES (2001, 'Milan Tour 2025', 899, 8, 1001);
INSERT INTO BOOKING (PID, email, booking_date, num_guests)
       VALUES (2001, 'alice@gmail.com', '2025-06-22', 2);   -- status left out → DEFAULT 'pending'

If the scenario says the row “already exists”, don't insert it again. Only insert what's new, e.g. a new student → STUDENT row + SIGNUP row.

4 · Triggers (SQL Server)

4.1 The mental model

A trigger is code that runs automatically when a table changes. In SQL Server:

  • It fires once per statement, not once per row. An INSERT of 3 rows fires it once.
  • Inside it you get two read-only tables: inserted (new versions of the changed rows) and deleted (old versions).
  • There is no NEW / OLD and no FOR EACH ROW. That syntax is Oracle/Postgres.
Statementinserted containsdeleted contains
INSERTthe new rowsempty
DELETEemptythe removed rows
UPDATErows after the changethe same rows before the change
UPDATE exampleUPDATE ORDER_ITEM SET quantity = 5 WHERE orderid = 7 AND productid = 3; (it was 2). Inside the trigger: deleted = (7, 3, qty 2, price 10), inserted = (7, 3, qty 5, price 10). The total must go up by 5×10 − 2×10 = 30.

4.2 Skeleton

CREATE TRIGGER trigger_name
ON table_name
AFTER INSERT          -- or AFTER INSERT, UPDATE, DELETE   or   INSTEAD OF INSERT
AS
BEGIN
   ...statements that use inserted / deleted...
END;

AFTER runs once the change has happened, and can still undo it with ROLLBACK. INSTEAD OF replaces the change; you have to redo it yourself if it's allowed.

4.3 Template A: reject a change (validation)

Each package can have at most 50 bookings (2025-26 S1, 9 marks):

CREATE TRIGGER booking_limit ON BOOKING
AFTER INSERT
AS
BEGIN
  IF EXISTS (
      SELECT B.PID
      FROM BOOKING B
      WHERE B.PID IN (SELECT PID FROM inserted)    -- only packages just touched
      GROUP BY B.PID
      HAVING COUNT(*) > 50                         -- AFTER trigger: new rows already counted
  )
  BEGIN
      RAISERROR('Booking limit of 50 exceeded', 16, 1);
      ROLLBACK TRANSACTION;                        -- undo the insert
  END
END;
Why “> 50” and not “>= 50”In an AFTER trigger the new booking is already in the table. Exactly 50 is allowed; 51 is not.

4.4 Template B: keep a derived value correct

ORDER.grandtotal must always equal SUM(quantity × price) of its items (2024-25 S2). Items can be inserted, updated or deleted, so all three must be handled. The easiest fully correct answer is one trigger that recomputes:

CREATE TRIGGER trg_item_total ON ORDER_ITEM
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
  UPDATE O
  SET grandtotal = ISNULL((SELECT SUM(I.quantity * I.price)
                           FROM ORDER_ITEM I
                           WHERE I.orderid = O.orderid), 0)
  FROM [ORDER] O
  WHERE O.orderid IN (SELECT orderid FROM inserted      -- orders affected by
                      UNION                              -- the new rows
                      SELECT orderid FROM deleted);      -- or the old rows
END;

Delta version (if they ask for separate triggers). INSERT: add the SUM from inserted. DELETE: subtract the SUM from deleted. UPDATE: do both.

CREATE TRIGGER trg_item_ins ON ORDER_ITEM AFTER INSERT AS
BEGIN
  UPDATE O SET grandtotal = O.grandtotal + X.s
  FROM [ORDER] O
  JOIN (SELECT orderid, SUM(quantity * price) AS s FROM inserted GROUP BY orderid) X
    ON O.orderid = X.orderid;
END;
Mistakes that lose marks
  • Only writing the INSERT trigger.
  • SET total = total + (SELECT qty*price FROM inserted): this errors when more than one row is inserted, and with no WHERE it updates every order.
  • Using NEW.qty / OLD.qty.
  • Bank-account version (2023-24 S2): a transfer subtracts from aid1 and adds to aid2, and aid2 is NULL for deposits and withdrawals.

4.5 Template C: automatic follow-up insert

CREATE TRIGGER newStudent ON STUDENT
AFTER INSERT
AS
BEGIN
  INSERT INTO MEMBERSHIP (cID, sID, position, yearJoin)
  SELECT 'SU001', sID, 'member', YEAR(GETDATE()) FROM inserted;

  INSERT INTO MEMBERSHIP (cID, sID, position, yearJoin)
  SELECT 'YWS012', sID, 'member', YEAR(GETDATE()) FROM inserted WHERE gender = 'female';
END;

4.6 Template D: act once when a threshold is reached

Reduce the fee by 10% when signups reach 1,000. Make sure it happens once, not on every later signup:

CREATE TRIGGER LowerProgramFee ON SIGNUP
AFTER INSERT
AS
BEGIN
  UPDATE PROGRAM SET Fee = Fee * 0.9
  WHERE PID IN (
    SELECT S.PID FROM SIGNUP S
    WHERE S.PID IN (SELECT PID FROM inserted)
    GROUP BY S.PID
    HAVING COUNT(*) >= 1000                                                -- now ≥ 1000
       AND COUNT(*) - (SELECT COUNT(*) FROM inserted I WHERE I.PID = S.PID) < 1000);  -- before < 1000
END;

4.7 “Describe the triggers, no code needed” (2025-26 S2)

Card.balance must match TxnLog (topup adds to card_from, spend subtracts, transfer moves money from card_from to card_to):

  • AFTER INSERT on TxnLog: for each new row, apply its effect. Topup: +amount on card_from. Spend: −amount on card_from. Transfer: −amount on card_from and +amount on card_to.
  • AFTER DELETE: reverse the effect of each deleted row.
  • AFTER UPDATE: reverse the old row (deleted), then apply the new row (inserted).
  • Optionally reject the change if a balance would go negative.

Enforcing a primary key with triggers: an INSTEAD OF / AFTER INSERT and UPDATE trigger that rejects (RAISERROR + ROLLBACK) if the new sid is NULL or already exists.

5.1 Views

CREATE VIEW PremierCustomer AS

FROM Customer C JOIN Owns O ON O.cid = C.cid JOIN Account A ON A.aid = O.aid

CREATE VIEW VIPStudent (Studentid, Studentname) AS     -- renamed columns

5.2 Indexes

An index is a sorted structure (a B+ tree) on one or more columns, so the database can jump straight to matching rows instead of scanning everything.

CREATE INDEX StudentIndex ON STUDENT (gender, age);

Composite index column order: columns tested with = first, then the column used in a range (>, <, BETWEEN) or ORDER BY.

Example (2025-26 S2)WHERE CountryNo = 8 AND Date > '2026-01-01' AND Date < '2026-02-01' ORDER BY Date → best index (CountryNo, Date). All CountryNo 8 entries sit together, already sorted by Date, so it's one contiguous scan and the ORDER BY comes free. With (Date, CountryNo), the country-8 rows are scattered through the date range.
Index on Price. Does it help…AnswerWhy
find MAX(Price)?Yesit's the last entry in the tree
find MAX(Quantity × Price)?Nothe tree is sorted by Price, not by the product
AVG(Price)?a littleit can read the smaller index instead of the table, but still has to read every entry
WHERE quantity > 10, index on quantityprobably notif most rows match (low selectivity), a full scan is just as fast

Downsides of indexes: slower INSERT/UPDATE/DELETE (the index must be updated too) and extra storage.

6 · Relational algebra, explained through SQL

Relational algebra (RA) is SQL written as maths. Everything works on sets, so there are never duplicate rows. If you can write the SQL, you can translate it.

In words: all − (all × required − actual).

6.2 Pattern 2: “at least N different X” → project, then γ

Worked example: students who took ≥ 3 different types with the same instructor (2025-26 S1). 
T   ← π sID, iID, type (ENROLLMENT)          -- STEP 1: remove repeat dates
C   ← γ sID, iID; COUNT(type)→n (T)          -- STEP 2: count per (student, instructor)
Ans ← π sID (σ n≥3 (C))                      -- STEP 3: filter, then project
SQL equivalent: SELECT DISTINCT sID FROM ENROLLMENT GROUP BY sID, iID HAVING COUNT(DISTINCT type) >= 3
Why step 1 mattersIf s1 took piano with i1 on 3 different dates, ENROLLMENT has 3 rows and counting them gives n = 3, even though it's only one type. The projection collapses them to one row (sets have no duplicates), so COUNT effectively becomes COUNT DISTINCT.

Without γ, for small N, self-join N copies and require the values to differ: σs1=s2=s3 ∧ i1=i2=i3 ∧ t1<t2 ∧ t2<t3(T1 × T2 × T3).

6.3 Pattern 3: “pairs who were together” → self-join

Worked example: pairs of customers in the same massage session at least 5 times (2024-25 S1). 
E1  ← ρ E1(c1, t1, d1, s1) (π cID, type, date, startTime (ENROLL))
E2  ← ρ E2(c2, t2, d2, s2) (π cID, type, date, startTime (ENROLL))
P   ← σ t1=t2 ∧ d1=d2 ∧ s1=s2 ∧ c1<c2 (E1 × E2)       -- same session, ordered pair
C   ← γ c1, c2; COUNT(d1)→n (π c1, c2, t1, d1, s1 (P))  -- one row per shared session
Ans ← π c1, c2 (σ n≥5 (C))

Why c1 < c2: with 3 people in one session, × gives 9 combinations. ≠ removes the 3 self-pairs and leaves 6, each pair twice. < leaves 3, one per pair.

6.4 Pattern 4: “the highest / most” → γ MAX, or “not beaten”

Worked example: lesson type(s) with the highest fee. Data: (a, 50), (b, 80), (c, 80).

With γ:

M   ← γ MAX(fee)→m (LESSON)                 -- one row: m = 80
Ans ← π type (σ fee = m (LESSON × M))       -- {b, c}

Without γ, the “not beaten” trick:

L1 ← ρ L1 (LESSON),  L2 ← ρ L2 (LESSON)
Beaten ← π L1.type (σ L1.fee < L2.fee (L1 × L2))   -- {a}: 50 < 80
Ans    ← π type (LESSON) − Beaten                    -- {b, c}
MistakeUsing ≤ instead of <. Every row is ≤ itself, so everything is “beaten” and the answer is empty.

“Most popular” = count first, then take the max of the counts: C ← γtype; COUNT(cID)→n(ENROLL), then apply pattern 4 to C. For “highest fee per hour”, compute it with an extended projection first: πtype, fee/duration→rate(LESSON).

6.5 Pattern 5: “only” / “never” → set difference

OnlyA  ← π sID (σ type='a' (Took)) − π sID (σ type≠'a' (Took))   -- took a and nothing else
NeverA ← π sID (STUDENT) − π sID (σ type='a' (Took))             -- never took a

7 · Functional dependencies: closure, keys, minimal basis

7.1 What an FD means

X → Y means: any two rows that agree on X must agree on Y. For example, StudentID → Name.

Checking an FD against a table (2023-24 S1)
ABCD
a1b1c1d1
a2b2c2d2
a3b1c1d1
a2b2c2d1
A → D? Violated: a2 appears with d2 and with d1. C → B? Holds: c1 always goes with b1, and c2 with b2.
One counter-example disproves an FD. A table can never prove one, because future data might break it. Answer with “holds in this instance”.

7.2 Closure X⁺: the tool you use for everything

X⁺ = every attribute X determines. Algorithm: start with X. Repeatedly, if the left side of an FD is inside your set, add its right side. Stop when nothing changes.

start{B, C}
1BC→D (B, C in set){B, C, D}
2D→E{B, C, D, E}
3E→A{A, B, C, D, E} = everything
So BC is a superkey. To prove an FD like BC→E, show E ∈ (BC)⁺. Write every step with the FD you used; that's where the marks are.

7.3 Finding ALL candidate keys

A superkey determines everything (X⁺ = all attributes). A candidate key is a minimal superkey: remove any attribute and it stops being one.

  1. Sort the attributes. Never on a right side → must be in every key. Only on right sides → in no key. Everything else → maybe.
  2. Compute the closure of the “must” set. If it's everything, that's the only key.
  3. Otherwise add “maybe” attributes one at a time, then two at a time…, and compute closures.
  4. Skip any set that contains a key you've already found (it wouldn't be minimal).
Worked example: R(A, B, C, D, E), F = {A→B, BC→D, D→E, E→A}
  • Right sides: B, D, E, A. C never appears on the right, so C is in every key.
  • C⁺ = {C}, not enough. Try adding one attribute:
  • AC⁺ = A C → B (A→B) → D (BC→D) → E (D→E) = all ✔
  • BC⁺ = all ✔ (shown above) · CD⁺ = C D E A B ✔ · CE⁺ = C E A B D ✔
  • Candidate keys: AC, BC, CD, CE. Prime attributes: A, B, C, D, E (all of them).
Trick question (2025-26 S1)“Which attributes must be in every key?” If every attribute appears on some right side, there may be keys with nothing in common. With F = {P→QR, Q→S, RS→T, ST→U, U→P}, both {P} and {U} are keys, so the answer is none (∅).

7.4 Minimal basis (minimal cover)

  1. Split right sides into single attributes: A→BC becomes A→B and A→C.
  2. Remove redundant FDs: for each FD X→A, temporarily delete it and compute X⁺ with the rest. If A is still in X⁺, the FD is redundant, so delete it for good.
  3. Shrink left sides: for each XY→A, if A ∈ X⁺ (using the full set), replace it with X→A.
  4. Recheck, because steps 2 and 3 can affect each other.
Worked example: F = {A→BC, B→C, AB→D}
  1. Split: A→B, A→C, B→C, AB→D
  2. Is A→C redundant? Without it, A⁺ = {A, B} → C via B→C. Yes, so remove it.
  3. AB→D: A⁺ = {A, B, C, D} already contains B, so B is extra. Replace it with A→D.
Minimal basis: {A→B, B→C, A→D}

8 · Normal forms: 3NF, BCNF, decomposition

8.1 Why normalise?

Redundancy causes anomalies. With Student(sid, name, course, lecturer) and course → lecturer:

  • Update anomaly: changing a course's lecturer means updating many rows. Miss one and the data contradicts itself.
  • Insertion anomaly: you can't record a new course's lecturer until some student takes the course.
  • Deletion anomaly: deleting the last student in a course loses who teaches it.

8.2 The definitions: test every FD

For each non-trivial FD X → Y (Y not inside X):

QuestionIf yes
1. Is X a superkey?OK for both BCNF and 3NF
2. If not, is every attribute of Y prime (part of some candidate key)?OK for 3NF, violates BCNF
3. Neither?Violates 3NF (and so BCNF)

BCNF: every FD passes test 1. 3NF: every FD passes test 1 or 2. So every BCNF relation is 3NF, and “BCNF but not 3NF” is impossible.

Three quick examples
  • R(A,B,C,D), F = {AB→C, C→D}. Key AB. C→D: C isn't a superkey and D isn't prime, so it fails 3NF.
  • R(A,B,C), F = {AB→C, C→B}. Keys AB and AC, so B is prime. C→B: C isn't a superkey, but B is prime, so it's 3NF, not BCNF.
  • R(A,B,C,D,E), F = {A→B, BC→D, D→E, E→A}. Keys AC, BC, CD, CE, so every attribute is prime. A→B fails BCNF, but B is prime, so it's 3NF, not BCNF.

8.3 Lossless join and dependency preservation

Lossless: joining the pieces gives back exactly the original table, with no fake rows. Test for two pieces: the shared attributes must be a key of at least one piece. That is, (R1 ∩ R2) → R1 or (R1 ∩ R2) → R2.

Dependency-preserving: every original FD can still be checked inside a single piece, or derived from the FDs that hold in the pieces.

Example: R(A, B, C), F = {AB→C, C→B}, split into R1(C, B) and R2(A, C).
  • Lossless? R1 ∩ R2 = {C}, and C→B means C is a key of R1. ✔ Lossless.
  • Preserving? C→B is checkable in R1. AB→C needs A, B and C together, which no piece has. ✘ AB→C is lost.

8.4 3NF decomposition (synthesis)

This method is always lossless and dependency-preserving.

  1. Find a minimal basis.
  2. Make one relation per FD, X ∪ Y. Merge FDs with the same left side if you like.
  3. If no relation contains a candidate key, add one relation that is just a key.
  4. Remove any relation that is a subset of another.
Worked example: R(A, B, C, D, E), F = {A→B, B→C, CD→E}
  • Key: A and D never appear on the right. AD⁺ = A D B C E = all, so key = AD.
  • F is already minimal. One relation per FD: (A, B), (B, C), (C, D, E).
  • Does any of them contain AD? No, so add (A, D).
  • 3NF: (A, B), (B, C), (C, D, E), (A, D)

8.5 BCNF decomposition

This method is always lossless, but may lose dependencies.

  1. Find an FD X → Y that violates BCNF (X is not a superkey of the current relation).
  2. Compute X⁺. Split R into R1 = X⁺ and R2 = X ∪ (R − X⁺).
  3. Project the FDs onto each piece: for subsets of the piece, compute closures using the original F, and keep only the attributes inside the piece.
  4. Repeat on any piece that still violates BCNF.
Worked example: same R(A, B, C, D, E), F = {A→B, B→C, CD→E}, key AD
  1. A→B violates (A isn't a superkey). A⁺ = {A, B, C}. Split into R1(A, B, C) and R2(A, D, E).
  2. R1(A, B, C): projected FDs A→B, B→C. Key A. B→C violates. B⁺ = {B, C}, so split into (B, C) and (A, B). Both are BCNF.
  3. R2(A, D, E): project. A⁺ = ABC, so nothing new in ADE. D⁺ = D. AD⁺ = all, so AD→E. Key AD, and this is BCNF.
BCNF: (A, B), (B, C), (A, D, E). Check CD→E: no piece contains C, D and E, and from {A→B, B→C, AD→E}, CD⁺ = {C, D}. So CD→E is lost.

8.6 “Compare and contrast 3NF and BCNF” (asked twice)

Model paragraphBoth decompositions are lossless. The 3NF result preserves every FD, but it may keep some redundancy: here, FDs whose right side is prime but whose left side isn't a key. The BCNF result removes all FD-based redundancy, but it lost [name the FD, e.g. CD→E], which can now only be checked by joining tables. BCNF is stricter (every BCNF relation is 3NF). Choose 3NF when enforcing every constraint matters; choose BCNF when avoiding redundancy matters more.

If R is already in 3NF (for example, all attributes are prime), say so: no 3NF decomposition is needed. Then show the BCNF decomposition and point out which FD it loses.

9.2 Subclasses (ISA)

A subclass is a special kind of the superclass: Physical Product isa Product. It inherits all the superclass's attributes and its key, and adds its own attributes and relationships. Constraints to state: disjoint vs overlapping (can a product be both kinds?) and total vs partial (must every product be one of the kinds?).

Three ways to turn ISA into tables (Product(pid, name, price), subclass PhysicalProduct with weight):

StyleTablesNote
ER-styleProduct(pid, name, price), PhysicalProduct(pid, weight)a physical product has a row in both
OO-styleProduct(pid, name, price), PhysicalProduct(pid, name, price, weight)each object is in exactly one table
NULL-styleProduct(pid, name, price, weight)weight is NULL for non-physical products

In every style, the subclass key is the superclass key. Never invent a new one.

9.3 Weak entities

A weak entity can't be identified by its own attributes. Room 101 exists in many hotels, so a Room is identified by its hotel's key + its own partial key: Room(hname, roomNo, type).

9.4 ER → tables (the forward direction)

  • Entity set → a table with its attributes, and its key as the key.
  • Many-many relationship → its own table: (key of E1, key of E2, relationship attributes), with both keys together as the key.
  • Many-one relationship → no new table. Put the “one” side's key as a foreign key in the “many” side's table.
  • Weak entity → owner's key + partial key.

9.5 Tables → ER (reverse engineering, asked 3 times)

Look at each table's key and its foreign keys:

Clue in the tableWhat to draw
Its own single key + plain attributes: F(W, Y)Entity set F, with attribute Y
A non-key column that is another table's key: B(X, H), where H is A's keyMany-one relationship B → A (arrow into A). Don't draw H as an attribute of B.
The key is just two other tables' keys: S(W, M)Many-many relationship between those two entities
The key = another table's key + an extra column: G(H, L, R)Weak entity G owned by A, partial key L
Several tables with the same key: C(M, K, X), D(M, N, H), E(M, P)ISA: the most general one (E) is the superclass, the others are subclasses

Worked example (2023-24 S2): A(H, Z), B(X, H), C(M, K, X), D(M, N, H), E(M, P), F(W, Y), G(H, L, R), S(W, M), U(H, M)
  • Entities: A (key H, attr Z), B (key X), F (key W, attr Y), E (key M, attr P).
  • B has H, A's key, as a non-key column → B —many-one→ A.
  • C, D, E share key M → C isa E (attr K), D isa E (attr N).
  • C has X → C —many-one→ B. D has H → D —many-one→ A.
  • G(H, L, R) → weak entity G, owner A, partial key L, attr R.
  • S(W, M) → many-many F — E. U(H, M) → many-many A — E.
Write your assumptions next to the diagram. Several readings can get full marks if they're justified.

9.6 Designing an ER diagram from a story

  1. Nouns that have their own properties → entity sets. Verbs that link them → relationships.
  2. For each relationship ask: “can one X have many Y? can one Y have many X?” That gives you the arrows.
  3. “Kinds of” something (Professor, PhD student, Researcher are all kinds of Person) → ISA. State disjoint/overlapping and total/partial.
  4. Something that only exists with an owner (a Grant only for a funded project) → a weak entity, or a subclass “FundedProject”.
  5. Write your assumptions.

Relational vs semi-structured (2024-25 S2, chat sessions): a session is a variable-length sequence of prompt/response turns. You can do it relationally, Session(sid, customer, start) + Turn(sid, turnNo, prompt, response, time), but nested or variable data like this fits more naturally in JSON/XML (semi-structured).

10.2 XML rules

  • Exactly one root element wraps everything.
  • Every tag is closed (<a>…</a> or <a/>), properly nested, and case-sensitive.
  • Attribute values are quoted: <Room currency="SGD">.

Final checklist for exam day
  • SQL: group by the id · DISTINCT where joins duplicate rows · ties → = MAX or ≥ ALL · “all” → double NOT EXISTS · “never” → NOT EXISTS · LEFT JOIN + COUNT(col) for zeros.
  • Triggers: inserted/deleted tables · set-based · cover INSERT, UPDATE and DELETE · RAISERROR + ROLLBACK.
  • RA: named steps · project before ÷ and before COUNT · rename for self-joins · < not ≤.
  • FDs: show every closure step · find all keys · prime → 3NF check · add the key relation in 3NF · project FDs in BCNF · name the lost FD.
  • ER: arrows into the “one” side · ISA from shared keys · weak entity from a composite key containing an FK · write assumptions.
  • XML: one root · * + ? · CDATA for attributes · IDs start with a letter.
