SQL — query templates

-- Division: "bought ALL X"  (double NOT EXISTS)
SELECT S.name FROM Student S
WHERE NOT EXISTS (SELECT * FROM Course C
  WHERE NOT EXISTS (SELECT * FROM Took T
    WHERE T.sid = S.sid AND T.cid = C.cid));

-- Ties / "the most" (return ALL tied)
... GROUP BY x HAVING COUNT(*) >= ALL
    (SELECT COUNT(*) FROM ... GROUP BY x);
-- or WHERE v = (SELECT MAX(v) FROM ...)

-- Group-wise max (per category, ties kept)
SELECT P.category, P.pname
FROM PRODUCT P JOIN ORDER_ITEM OI ON ...
GROUP BY P.productid, P.category, P.pname
HAVING SUM(OI.price*OI.quantity) >= ALL (
  SELECT SUM(OI2.price*OI2.quantity)
  FROM PRODUCT P2 JOIN ORDER_ITEM OI2 ON ...
  WHERE P2.category = P.category
  GROUP BY P2.productid);

-- Pairs "together" (self-join, no dup pairs)
FROM T A JOIN T B ON A.sess = B.sess
  AND A.sid < B.sid

-- Both X and Y
WHERE EXISTS(..X..) AND EXISTS(..Y..)
-- or HAVING COUNT(DISTINCT cat) = 2

-- "Never did X" -> NOT EXISTS (not NOT IN)
-- "No JOIN allowed" -> nested IN / EXISTS

SQL — traps

  • Inner join drops unmatched rows, so no 0 counts. LEFT JOIN + COUNT(*) → 1, LEFT JOIN + COUNT(col) → 0.
  • OR join (from=id OR to=id): count every matching pair.
  • NULL: NOT IN and >= ALL → empty if the subquery has a NULL. x <> 2 drops NULL rows. Aggregates skip NULLs, and AVG = SUM / non-null count.
  • IS NULL / IS NOT NULL, never = NULL.
  • WHERE = row filter, before GROUP BY, no aggregates. HAVING = group filter.
  • Every non-aggregated SELECT column must be in GROUP BY. Group by the id, not just the name (names can repeat).
  • DISTINCT when joins can duplicate names. COUNT(DISTINCT x) for “different X”.
  • Dates: '2025-01-03', YEAR(d), MONTH(d), FORMAT(d,'yyyy-MM'), GETDATE(), BETWEEN.
  • LIKE: 'J%' starts with J, '%Fashion%' contains. Reserved names: [ORDER], [USER].
  • UNION removes duplicates; UNION ALL keeps them. Add a constant column: SELECT TID, Tname, 'Trainer' AS Role.
  • Conditional count: SUM(CASE WHEN gender='M' THEN 1 ELSE 0 END).
  • If a query “can't be constructed”, say why (a missing link or attribute). Some papers offer this option.

DDL / INSERT

CREATE TABLE BOOKING (
  PID          INT NOT NULL,
  email        VARCHAR(100) NOT NULL,
  booking_date DATE NOT NULL,
  num_guests   INT CHECK (num_guests > 0),
  status VARCHAR(10) NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending','confirmed','cancelled')),
  PRIMARY KEY (PID, email, booking_date),
  FOREIGN KEY (PID) REFERENCES PACKAGE(PID),
  FOREIGN KEY (email) REFERENCES [USER](email)
    ON DELETE CASCADE
);
INSERT INTO T (c1, c2) VALUES (1, 'x');
  • INSERT parents before children (FK order).
  • Leave out a DEFAULT column to get the default. 4-digit id → INT. Money → DECIMAL(10,2).
  • Constraint options: key · NOT NULL · attribute CHECK · tuple CHECK · ASSERTION (multi-table, checked on every change) · trigger.

Triggers (SQL Server)

CREATE TRIGGER name ON T
AFTER INSERT, UPDATE, DELETE   -- or INSTEAD OF
AS
BEGIN
  -- inserted = new rows, deleted = old rows
  IF EXISTS (SELECT ... FROM inserted ...)
  BEGIN
    RAISERROR('message', 16, 1);
    ROLLBACK TRANSACTION;
  END
END;

-- Safest "keep total consistent" (one trigger):
CREATE TRIGGER trg_total ON ORDER_ITEM
AFTER INSERT, UPDATE, DELETE AS
BEGIN
  UPDATE O SET grandtotal = ISNULL((
      SELECT SUM(I.quantity*I.price)
      FROM ORDER_ITEM I
      WHERE I.orderid = O.orderid), 0)
  FROM [ORDER] O
  WHERE O.orderid IN (SELECT orderid FROM inserted
                      UNION SELECT orderid FROM deleted);
END;
  • Fires once per statement. inserted/deleted are tables that can hold many rows. No NEW/OLD, no FOR EACH ROW.
  • INSERT fills inserted · DELETE fills deleted · UPDATE fills both.
  • Delta style: add the SUM from inserted, subtract the SUM from deleted, grouped by key.
  • Limit check: count AFTER the insert, so test > limit.
  • Threshold “reaches 1000”: fire once, when the count before was < 1000 and now ≥ 1000.

Views · Index

CREATE VIEW V(colA, colB) AS SELECT ...;
  • View: a stored query, rerun on use, always current. Materialized: stored result, fast to read, must be refreshed, takes space. Temporary: session only.
  • Pros of views: security (hide columns), simpler queries, logical independence.
  • CREATE INDEX StudentIndex ON STUDENT(gender, age);
  • Composite: equality columns first, then the range/ORDER BY column.
  • A tree index on x helps MIN/MAX(x) and range on x. It does not help MAX(x*y), or filters that match most rows (low selectivity).
  • Downsides: slower INSERT/UPDATE/DELETE, extra storage.

FDs & normal forms

  • X⁺: keep adding the RHS of any FD whose LHS ⊆ the current set.
  • Keys: attributes on no RHS are in every key. Attributes only on a RHS are in none. Grow from the core and check minimality.
  • Prime = in some candidate key.
  • BCNF: every non-trivial X→Y has X a superkey.
  • 3NF: X is a superkey or Y is prime. BCNF ⊂ 3NF.
  • Minimal basis: (1) split the RHS (2) drop redundant FDs (3) shrink the LHS. Recheck.
  • 3NF synthesis: minimal basis → one relation per FD → add a key relation if none contains a key → drop subsets.
  • BCNF decomposition: violating X→Y → split into (X⁺) and (X ∪ (R−X⁺)) → project the FDs (compute closures inside each piece) → repeat.
  • Lossless (2 pieces): R1∩R2 → R1 or R1∩R2 → R2.
  • Preserving: each FD derivable from the union of the projected FDs. Name the lost FD.
  • Compare: BCNF has no FD redundancy and is lossless, but may lose FDs. 3NF is lossless and preserving, but may keep redundancy.
  • Check an FD on an instance: the same X value with different Y values means it's violated. One counter-example disproves; an instance can never prove an FD.
  • Anomalies: update, insertion, deletion.
  • Adding an FD never removes an implied FD.

ER

  • □ entity · ⬭ attribute (underlined = key) · ◇ relationship · △ ISA · double □/◇ = weak entity/identifying relationship.
  • Arrow → the “one” side. Arrows both ways = one-one. Rounded arrow = exactly one.
  • ER → relations: entity → table. Many-many → table (both keys). Many-one → put the FK in the “many” side. Weak → owner key + partial key.
  • ISA: ER-style (sub = super key + own attributes) · OO-style (a table per combination with all attributes) · NULL-style (one table). Subclass key = superclass key.
  • Constraints: disjoint vs overlapping · total vs partial. State your assumptions.

XML · DTD · JSON

<!DOCTYPE Hotels [
<!ELEMENT Hotels (Hotel*)>
<!ELEMENT Hotel (Hname, Address, Room+)>
<!ELEMENT Address (UnitNo, StreetName, Zipcode, Country)>
<!ELEMENT Room (RoomNo, Type, Price)>
<!ATTLIST Price currency CDATA #FIXED "SGD">
<!ELEMENT Hname (#PCDATA)>  ... one per leaf
]>
<!ATTLIST Post pid ID #REQUIRED author IDREF #REQUIRED>
  • none = exactly 1 · ? 0–1 · * 0+ · + 1+ · | choice.
  • Attribute defaults: #REQUIRED · #IMPLIED · #FIXED "v" · "default". Attribute type CDATA, never #PCDATA.
  • ID values: unique, start with a letter or _, no spaces.
  • XML has exactly one root, case-sensitive tags, every tag closed, attribute values quoted.
  • JSON → XML: object → element, array → repeated elements, wrapped in a root.
  • Structured (fixed schema, tables) · semi-structured (self-describing tags: XML, JSON) · unstructured (text, images). Semi-structured fits variable or nested data, like chat sessions.
