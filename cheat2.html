1 · SQL semantics

Three-valued logic (TRUE / FALSE / UNKNOWN)

Any comparison with NULL is UNKNOWN. Think T = 1, U = ½, F = 0: AND = min, OR = max, NOT x = 1 − x.

xyx AND yx OR yNOT x
TUUTF
FUFUT
UUUUU
  • WHERE, HAVING and ON keep only TRUE, so UNKNOWN rows are dropped. Textbook trap: WHERE length <= 120 OR length > 120 does not return every movie, because rows with NULL length give U OR U = U.
  • A CHECK constraint rejects only FALSE, so UNKNOWN passes. CHECK (age > 0) accepts age = NULL. Add NOT NULL if NULL must be rejected.
  • NOT(UNKNOWN) = UNKNOWN, so WHERE NOT (x = 5) still drops rows where x is NULL.
  • Arithmetic with NULL gives NULL: NULL + 5, price * NULL.
  • Where NULLs are treated as equal: GROUP BY (all NULLs form one group), DISTINCT, and UNION/INTERSECT/EXCEPT. In SQL Server, a UNIQUE column allows only one NULL.

  • Empty-set trap: HAVING COUNT(*) >= ALL (subquery) is TRUE for every row if the correlated subquery returns nothing, so you get extra rows. = (SELECT MAX(...)) on an empty set compares with NULL, so you get no rows.
  • x <> ANY (S) means "differs from at least one value". It is not the same as NOT IN. With S = {1, 2}, every x satisfies it.
  • When S contains a NULL: x IN (1, NULL) is TRUE if x = 1, otherwise UNKNOWN. x > ALL (1, NULL) can never be TRUE.
  • A scalar subquery (x = (SELECT ...)) that returns more than one row is a runtime error. If it returns 0 rows, the value is NULL.
  • Inside EXISTS, the SELECT list doesn't matter: SELECT *, SELECT 1 and SELECT NULL behave the same.

Outer joins: which NULLs appear

Example data: R(a, b) = {(1, x), (2, y)} and S(b, c) = {(x, 10), (z, 30)}. A row with no match is called dangling. An outer join keeps it and fills the other table's columns with NULL.

R ? JOIN S ON R.b = S.bRows (a, R.b, S.b, c)
INNER(1, x, x, 10)
LEFT (RA ⟕)+ (2, y, NULL, NULL)
RIGHT (RA ⟖)(1, x, x, 10), (NULL, NULL, z, 30)
FULL (RA ⟗)all 3 rows above
-- Trap: a WHERE condition on the right table undoes the LEFT JOIN
SELECT S.name, COUNT(A.aid) FROM STUDENT S
LEFT JOIN ACTIVITY A ON A.sid = S.sid AND A.year = 2024  -- keeps 0-count students
-- WHERE A.year = 2024   <- NULL = 2024 is UNKNOWN, so dangling rows go (= inner join)
GROUP BY S.sid, S.name;
-- Anti-join ("never"): LEFT JOIN ... WHERE A.sid IS NULL

SQL Server has no NATURAL JOIN, so always write ON.

UNION / INTERSECT / EXCEPT: set vs bag

  • A plain SELECT returns a bag (duplicates kept). UNION, INTERSECT and EXCEPT remove duplicates by default. Add ALL to keep them.
  • If a row appears m times in R and n times in S: UNION ALL gives m + n copies, INTERSECT ALL gives min(m, n), EXCEPT ALL gives max(m − n, 0). SQL Server supports only UNION ALL.
  • Columns are matched by position, not by name, and their types must be compatible. Result column names come from the first query. You can only have one ORDER BY, at the very end.
-- students who took DB but not OS (EXCEPT = RA "−")
SELECT sid FROM Took WHERE cid = 'DB'
EXCEPT
SELECT sid FROM Took WHERE cid = 'OS';

Evaluation order, correlation, CASE

Logical order: FROM/JOIN…ON → WHERE → GROUP BY → HAVING → SELECT (aliases, then DISTINCT) → ORDER BY → TOP. Many errors follow from this order:

  • A SELECT alias can't be used in WHERE, GROUP BY or HAVING, because it doesn't exist yet at that point. It can be used in ORDER BY.
  • ORDER BY can use a column you didn't select, unless you use SELECT DISTINCT. Sorting defaults to ASC, so "most recent first" needs ORDER BY yearFounded DESC.
  • Uncorrelated subquery: runs once. Correlated subquery: refers to the outer query's alias, so it re-runs for every outer row.
  • Scope trap: an unqualified column that the inner table doesn't have silently binds to the outer table. WHERE sid IN (SELECT sid FROM Course), with no sid column in Course, returns every row. Always qualify your columns.
SELECT name,
  CASE WHEN score >= 80 THEN 'A'
       WHEN score >= 65 THEN 'B'      -- the first true WHEN wins
       ELSE 'C' END AS grade          -- no ELSE means NULL
FROM Result;
-- Pivot: SUM(CASE WHEN YEAR(d)=2024 THEN amt ELSE 0 END) AS y2024

2 · Views, constraints, referential integrity, triggers

Materialized views in depth

A normal view stores only the query text, so every use reruns the query. A materialized view (MV) runs the query once and stores the result rows on disk, like a table. Reads are fast because no join or aggregation happens at read time. The stored copy goes stale when the base tables change, so it has to be maintained (refreshed).

  • When to refresh. Immediate: in the same transaction as each base-table change. Always fresh, but every INSERT, UPDATE and DELETE gets slower. Deferred: at commit, on demand, or the next time someone reads it. Periodic: on a schedule, e.g. nightly. Reads may be stale in between, which is fine for reports.
  • How to refresh. Full (complete): rerun the whole query. Simple but expensive. Incremental (fast): apply only the changes. For MV = R ⋈ S: inserting r into R adds r ⋈ S to the MV, and deleting r removes the MV rows built from r. This is easy for select-project-join queries and for SUM/COUNT. It's hard for MIN/MAX after a delete (if you delete the max, you have to recompute it) and for DISTINCT.
  • Query rewriting: the optimizer can answer a query on the base tables from an MV that covers it, even if the query never mentions the MV.
-- Textbook (Ullman 8.5)
CREATE MATERIALIZED VIEW MovieProd AS
  SELECT title, year, name FROM Movies, MovieExec WHERE producerC# = cert#;

-- SQL Server: an "indexed view" is its materialized view
CREATE VIEW dbo.SalesByProduct WITH SCHEMABINDING AS   -- base tables are locked against changes
SELECT OI.productid,
       SUM(OI.quantity * OI.price) AS total,
       COUNT_BIG(*) AS n                    -- required when there is a GROUP BY
FROM dbo.ORDER_ITEM OI                      -- two-part names (dbo.X) required
GROUP BY OI.productid;
CREATE UNIQUE CLUSTERED INDEX IX_SBP ON dbo.SalesByProduct(productid);  -- THIS step stores the rows

-- Oracle:   CREATE MATERIALIZED VIEW mv REFRESH COMPLETE ON DEMAND AS SELECT ...;
-- Postgres: CREATE MATERIALIZED VIEW mv AS SELECT ...;   REFRESH MATERIALIZED VIEW mv;
  • SQL Server maintains indexed views immediately, so they're never stale, but writes are slower. They don't allow OUTER JOIN, DISTINCT, subqueries, TOP, UNION or AVG/MIN/MAX. Store SUM and COUNT_BIG instead, and compute an average as SUM/COUNT.
  • Good when an expensive join or aggregate is read often and its base data changes rarely: dashboards, reports, data warehouses.
  • Bad when the base tables are updated heavily (every write pays the maintenance cost), when results must be exactly current, or when storage is tight.

Updatable views, WITH CHECK OPTION, INSTEAD OF triggers

You can only change data through a view if each view row maps to exactly one base row. Standard SQL rules for an updatable view: one table in FROM, no DISTINCT, no GROUP BY or aggregates, the table isn't used again in a subquery in WHERE, and SELECT includes enough columns that an INSERT can fill the rest with NULL or defaults. SQL Server also allows views with joins, but each INSERT or UPDATE can touch columns of only one base table.

CREATE VIEW ParamountMovies AS
  SELECT title, year FROM Movies WHERE studioName = 'Paramount';
INSERT INTO ParamountMovies VALUES ('Star Trek', 1979);
-- stored with studioName NULL, so the new row VANISHES from the view

-- Fix 1: include studioName in the view, and end it with ... WITH CHECK OPTION;
--        which rejects INSERTs/UPDATEs whose rows wouldn't satisfy the view's WHERE
-- Fix 2: an INSTEAD OF trigger supplies the hidden value
CREATE TRIGGER ParamountInsert ON ParamountMovies
INSTEAD OF INSERT AS
  INSERT INTO Movies (title, year, studioName)
  SELECT title, year, 'Paramount' FROM inserted;

INSTEAD OF triggers can make any view updatable. In SQL Server, views accept only INSTEAD OF triggers, not AFTER triggers. If asked whether a view can be updated, check for DISTINCT, aggregates, several tables, and NOT NULL columns missing from the view.

Constraints in depth: CHECK vs ASSERTION vs trigger (2024-25 S1 Q4b)

  • Attribute-based CHECK (written on a column): checked only when a row is inserted or that column is updated. Limitation: standard SQL lets it contain a subquery on another table, but changes to that other table won't re-check it, so it can quietly become false. SQL Server doesn't allow subqueries in CHECK at all.
  • Tuple-based CHECK (written at table level, can use several columns of the same row): checked when a row is inserted or updated. A DELETE never runs any CHECK.
  • Assertion: a schema-level condition over any tables. It's checked after every INSERT, UPDATE or DELETE on any table it mentions. It's the most complete option but expensive, and SQL Server doesn't implement it.
  • Trigger: event → condition → action. It fires only on the events and table you list, so imitating an assertion takes one trigger per table and event. Unlike the others, it can also do things, not just reject changes.
-- Assertion: every program has at least one class (no FK can say this)
CREATE ASSERTION ProgramHasClass CHECK (NOT EXISTS (
  SELECT * FROM PROGRAM P WHERE NOT EXISTS (SELECT * FROM CLASS C WHERE C.PID = P.PID)));
-- Deleting a CLASS row can break this rule; a CHECK on PROGRAM would never notice.

-- Named constraints can be added and dropped later
CREATE TABLE PROGRAM (PID INT PRIMARY KEY, Pname VARCHAR(50),
  Fee DECIMAL(10,2) CONSTRAINT chk_fee CHECK (Fee > 0));
ALTER TABLE PROGRAM ADD CONSTRAINT uq_pname UNIQUE (Pname);
ALTER TABLE PROGRAM DROP CONSTRAINT chk_fee;

Model answer: (1) Key, FK and CHECK constraints are local to one table and are checked only when that row or column changes. (2) Triggers run custom code on specific events. (3) Assertions are database-wide conditions. For "validation across more than one table, checked on every insert, update or delete", the answer is assertion.

Referential integrity: the policies in detail

ChangeWhat happens
INSERT a child row, or UPDATE its FK, to a value that isn't in the parentAlways rejected. The policies below don't apply.
DELETE a parent row, or UPDATE a parent keyHandled by the policy you chose, set separately for ON DELETE and ON UPDATE
  • Default / NO ACTION: the parent change is rejected if any child row still refers to it.
  • CASCADE: deleting a parent deletes its children. Updating a parent key from 123 to 456 changes the children's FK to 456 as well.
  • SET NULL: the children's FK becomes NULL (the column must allow NULL). SQL Server also has SET DEFAULT.
  • A NULL FK value isn't checked; it means "no parent".
  • Deferred checking (DEFERRABLE INITIALLY DEFERRED) checks the FK only at COMMIT. You need it when two tables reference each other. SQL Server doesn't support it.
FOREIGN KEY (presC) REFERENCES MovieExec(cert)
  ON DELETE SET NULL      -- exec deleted: keep the movie, president unknown
  ON UPDATE CASCADE       -- exec's cert changes: follow it

Justify your choice. CASCADE suits rows that only exist because of the parent, like order items. SET NULL suits an optional link. NO ACTION (reject) suits cases where history must be kept.

Trigger terminology and textbook (standard SQL) syntax

  • ECA rule: Event = INSERT, DELETE, or UPDATE [OF col] ON table. Condition = the WHEN clause; if it isn't TRUE, nothing happens. Action = one SQL statement or a BEGIN…END block.
  • Timing: BEFORE, AFTER or INSTEAD OF. SQL Server has only AFTER (FOR means the same thing) and INSTEAD OF.
  • Row-level (FOR EACH ROW) runs once per changed row and sees OLD ROW and NEW ROW. Statement-level (FOR EACH STATEMENT, the default) runs once per statement and sees OLD TABLE and NEW TABLE.
  • SQL Server triggers are statement-level only: deleted ≈ OLD TABLE, inserted ≈ NEW TABLE, and IF UPDATE(col) ≈ "UPDATE OF col".
-- Textbook: never let a net worth go down (row-level)
CREATE TRIGGER NetWorthTrigger
AFTER UPDATE OF netWorth ON MovieExec          -- event
REFERENCING OLD ROW AS OldTuple, NEW ROW AS NewTuple
FOR EACH ROW
WHEN (OldTuple.netWorth > NewTuple.netWorth)   -- condition
  UPDATE MovieExec SET netWorth = OldTuple.netWorth WHERE cert = NewTuple.cert;  -- action

-- The same in SQL Server (set-based)
CREATE TRIGGER NetWorthTrigger ON MovieExec AFTER UPDATE AS
IF UPDATE(netWorth)
  UPDATE M SET netWorth = d.netWorth
  FROM MovieExec M JOIN deleted d ON d.cert = M.cert JOIN inserted i ON i.cert = d.cert
  WHERE d.netWorth > i.netWorth;

Enforcing a primary key with triggers instead of PRIMARY KEY (2025-26 S2 Q4c)

A primary key means not NULL + unique. Only INSERT and UPDATE can break it, never DELETE. So you need AFTER INSERT and AFTER UPDATE triggers. They check the table after the change, which also catches duplicates within a single multi-row INSERT.

CREATE TRIGGER trg_student_pk ON Student
AFTER INSERT, UPDATE
AS
BEGIN
  IF EXISTS (SELECT * FROM inserted WHERE sid IS NULL)
     OR EXISTS (SELECT S.sid FROM Student S
                WHERE S.sid IN (SELECT sid FROM inserted)
                GROUP BY S.sid HAVING COUNT(*) > 1)
  BEGIN
    RAISERROR('Primary key violation on Student.sid', 16, 1);
    ROLLBACK TRANSACTION;
  END
END;

A deeper point worth making: without a real PK, Holds.sid and TxnLog.sid can't be declared as FKs (an FK must reference a PK or UNIQUE column). So referential integrity also needs triggers: on INSERT/UPDATE of a child, the sid must exist in Student; on DELETE/UPDATE of a Student, reject (or cascade) if the sid is still referenced.

3 · Indexes: theory and the "why"

Clustered vs non-clustered, B+ tree vs hash, covering indexes

  • Clustered index: the table's rows themselves are stored in key order (the leaf level is the data). There can be only one per table. In SQL Server the PRIMARY KEY becomes the clustered index by default. Matching rows sit next to each other, so even a wide range is one contiguous read.
  • Non-clustered (secondary) index: a separate sorted structure whose leaves point to the rows. You can have many. Each match may cost an extra random page read to fetch the row (a "lookup"). That's why it only pays off when few rows match. If most rows match (low selectivity), one sequential scan is cheaper, and the optimizer ignores the index.
  • B+ tree: balanced, with linked leaves. Supports =, ranges, ORDER BY, MIN/MAX and LIKE 'abc%'. Hash index: equality only, about one I/O, but no ranges and no ordering.
  • Covering index: contains every column the query needs, so the table is never read: CREATE INDEX ix_q ON PRODUCT(quantity) INCLUDE (pname);
  • The index can't be used for a seek when the column is wrapped in a function (WHERE YEAR(d) = 2024; rewrite as d >= '2024-01-01' AND d < '2025-01-01'), when the pattern starts with a wildcard (LIKE '%x'), or when the first column of a composite index isn't filtered (an index on (a, b) doesn't help WHERE b = 5).

Model answers (2024-25 S2 Q4c). (i) Index on quantity, query WHERE quantity > 10: it depends on selectivity. If only a few products match, yes: a seek plus a few lookups. If most match, no: a lookup per row costs more than a full scan. pname isn't in the index, so every match needs a lookup. (ii) AVG(price) with an index on price: there's no filter, so every price must still be read, and the tree can't skip anything. (MIN/MAX are different: they read just one end of the tree.) At best, scanning the narrower index instead of the table saves a little I/O.

Textbook cost model: should we build the index?

StarsIn takes 10 pages. Q1 finds the movies of a star s; Q2 finds the stars of a movie m. Each star or movie has 3 rows, on 3 different pages. Reading an index page costs 1 I/O. Modifying a page costs 2 (read + write) for the table, plus 2 per index. Q1 and Q2 happen with probabilities p1 and p2; an INSERT happens the rest of the time (1 − p1 − p2).

Chase test: lossless join for any number of pieces

The two-piece rule only works for binary splits. The chase works for any decomposition.

  • Make one row per piece. Use a plain letter (a, b…) for each attribute in that piece, and a subscripted letter (b1, c2…) for every other attribute.
  • For each FD X→Y: if two rows agree on X, make them agree on Y. If either symbol is plain, use the plain one. Replace the symbol everywhere in that column.
  • Repeat until nothing changes. If some row is entirely plain letters, the decomposition is lossless. If not, the final table is a counterexample.

R(A,B,C,D), F = {A→B, B→C, CD→A}, pieces S1(A,D), S2(A,C), S3(B,C,D):

ABCD

S3a3bcd
A→B: S1 and S2 agree on a, so b2 := b1. B→C: S1 and S2 agree on b1, so c1 := c. Now S1 = (a, b1, c, d).
CD→A: S1 and S3 agree on (c, d), so a3 := a. Now S3 = (a, b, c, d), all plain, so it's lossless ✔

Lossy example: R(A,B,C), F = {A→B}, pieces (A,B) and (B,C). The rows are (a, b, c1) and (a2, b, c). They never agree on A, so nothing changes and neither row becomes all plain: lossy. The join creates the fake rows (a, b, c) and (a2, b, c1).

Dependency preservation: the correct test

Seeing an FD inside one piece is enough to show it's preserved, but not seeing it doesn't prove it's lost. It might follow from FDs in several pieces combined. Use this algorithm, which needs only closures under the original F:

for each X→Y in F:
   Z := X
   repeat  for each piece Ri:  Z := Z ∪ ( (Z ∩ Ri)⁺ ∩ Ri )
   until Z stops changing
   X→Y is preserved  iff  Y ⊆ Z

"Explain with examples how BCNF improves on 3NF" (2025-26 S2 Q1b)

Core idea: 3NF still allows an FD X→A where X is not a superkey, as long as A is prime. That FD still repeats the same fact across many rows. BCNF forbids it: the left side of every non-trivial FD must be a superkey, so each fact is stored once.

Example: Teach(student, course, tutor), where tutor → course (each tutor teaches one course) and student, course → tutor. The keys are {student, course} and {student, tutor}. Every attribute is prime, so the table is 3NF. But tutor → course has a non-superkey on the left, so it's not BCNF.

  • Redundancy: "Tan teaches DB" is stored 3 times. Update anomaly: moving Tan to another course means changing 3 rows. Insertion anomaly: you can't record that a new tutor Lee teaches DB until a student has Lee. Deletion anomaly: deleting Ann's OS row loses the fact that Lim teaches OS.
  • BCNF fix: tutor⁺ = {tutor, course}, giving R1(tutor, course) and R2(student, tutor). It's lossless because the shared attribute, tutor, is the key of R1. All three anomalies are gone.
  • The cost: student, course → tutor is lost. Nothing stops Ann from getting two DB tutors without a join or a trigger.

The ladder: 2NF removes non-prime attributes that depend on part of a key. 3NF removes non-prime attributes that depend on another non-key attribute (transitive). BCNF removes any FD whose left side isn't a superkey, even when the right side is prime.

3NF theory on a data instance (2023-24 S1 Q2b, Q2c)

R(A,B,C,D), F = {AB→C, C→B, A→D}. A is in every key. A⁺ = AD, AB⁺ = ABCD, AC⁺ = ACBD, so the keys are AB and AC. A, B, C are prime; D is not.

  • A→D violates 3NF: A isn't a superkey and D isn't prime. It's a partial dependency: a non-prime attribute depends on part of a key, which also fails 2NF. C→B is fine for 3NF (B is prime) but violates BCNF.
  • Consequences, shown on the data: D repeats in every row with the same A (a1 appears 3 times with d1). Update anomaly: change D in one a1 row and the rows contradict each other. The given data already shows this: a2 has both d2 and d1. Insertion anomaly: you can't record "a5 has d3" without values for B and C. Deletion anomaly: deleting the only a3 row loses the fact that a3 maps to d1.
  • 3NF synthesis: one relation per FD gives (A,B,C), (C,B), (A,D). Drop (C,B) because it's inside (A,B,C), which already contains the key AB. Result: R1(A,B,C), R2(A,D).
  • "Are the new relations necessarily smaller?" No. Each has fewer attributes, but the join attribute (A) is stored in several tables, the total number of columns grows, and queries need joins. The row count may shrink because projection removes duplicates: R1 has 4 rows and R2 has 5, versus 7 in R.
  • Other improvements: (1) go to BCNF by splitting R1 on C→B into (C,B) and (A,C), which loses AB→C. (2) Declare PRIMARY KEY(A,B) to stop the duplicate rows in the instance. (3) Clean up the inconsistent a2 rows before enforcing A→D.

1NF, 2NF, MVDs and 4NF

4NF ⊂ BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF.

  • 1NF: every value is atomic. No lists in a cell (phones = "9123, 8456" ✘).
  • 2NF: 1NF and no partial dependency. Example: Enroll(sid, cid, sname, grade) with sid → sname. sname depends on only part of the key, so it fails 2NF. Fix: Student(sid, sname) and Enroll(sid, cid, grade). If every key is a single attribute, the table is automatically 2NF.
  • MVD X ↠ Y: for a given X, the set of Y values doesn't depend on the other attributes. If two rows agree on X, swapping their Y values gives rows that are also in the table. Every FD is also an MVD.

6 · ER design

Subclass and "isa": the theory answer and how to draw it (2025-26 S1 Q2a)

Model answer: a subclass is an entity set whose members are a special subset of a superclass. Its members have extra attributes or relationships that the other members don't. The isa relationship (a triangle pointing to the superclass) says every subclass entity is also a superclass entity, matched one-to-one. It gives: inheritance (the subclass inherits all attributes, the key and the relationships, so you only draw what it adds); no irrelevant attributes (putting weight on Products would leave it NULL for every digital product); and relationships specific to the subclass (only physical products are stored in a Warehouse).

          (pid)  (name)  (price)  (brand)
                  [ Products ]
                  /          \
               /isa\        /isa\
                 |            |
   [Physical Products]   [Digital Products]
   (weight)(dimensions)   (fileSizeMB)(format)
   (stockQty)             (downloadURL)
   written by the triangles: {disjoint, total}

The key of Physical Products is pid, inherited. Never give a subclass its own key.

ER design principles, and entity vs attribute

  • Faithfulness: the model must match reality. Don't make Teaches many-one if a course can have co-lecturers.
  • Avoid redundancy: say each fact once. Giving Movies a studioName attribute and an Owns relationship to Studios is wrong ✘, because it leads to update anomalies.
  • Simplicity: don't add entity sets or relationships you don't need, or ones that can be derived from others.
  • Entity or attribute? Make E an attribute only if (1) every relationship involving E has its arrow pointing into E, (2) E's only key is all of its attributes (usually just one), and (3) no relationship involves E more than once. If Studio has only a name, make studioName an attribute of Movies. If it has an address, keep it as an entity.
  • Weak entities: the supporting relationship must be many-one from the weak entity to its owner, with referential integrity (rounded arrow, double diamond). The key is the owner's key plus the partial key (dashed underline). Use them sparingly: if a natural unique ID exists, use an ordinary entity.

If asked to "critique this ER design", look for redundant attributes or relationships, wrong arrows, and one-attribute entities that should be attributes.

Multiway relationships, roles, relationship attributes, degree constraints

Multiway arrow: in Contracts(Stars, Movies, Studios), an arrow into Studios means each (star, movie) pair relates to at most one studio.

Converting to binary: replace the diamond with a connecting entity set that has a many-one relationship to each participant. Any relationship attributes move onto the new entity.

Stars ◇ Movies ◇ Studios (Contracts, salary)   ⇒   Contract(salary) ──▶ Stars, ──▶ Movies, ──▶ Studios
Relation: Contracts(starName, title, year, studioName, salary)

Roles: when the same entity set appears twice in one relationship, label each edge with its role (e.g. "parent" and "child"). The relation then needs renamed columns:

Traveller ◇ Parent ◇ Traveller  (edges "parent", "child")
PARENT(parentTravellerID, childTravellerID)  -- both are FKs to TRAVELLER; key = both (many-many)

Relationship attributes describe the combination, not either entity on its own. Examples: grade on Enrolls(Student, Course), salary on Contracts.

Chat-session ER and "is the relational model suitable?" (2024-25 S2 Q1a)

A Turn only exists inside its session and is numbered within it, so it's a weak entity with key (sessionID, turnNo). Tables: Customer(custID, …) · Session(sessionID, custID, …) · Turn(sessionID, turnNo, prompt, response, …).

For relationalAgainst relational
Metadata (who, when) is fixed and structured. FKs enforce integrity. SQL makes analytics easy (sessions per customer). ACID transactions. Prompts and responses are free text. Sessions vary in length, and the order must be rebuilt with turnNo + ORDER BY. Responses can contain nested content (code, images), so the schema keeps changing or fills with NULLs. A session is always read as a whole, which suits a document.

Conclusion: a hybrid. Use relational tables for customers and sessions, and store each transcript as a JSON document (in a document store, or in an NVARCHAR(MAX) column queried with JSON_VALUE/OPENJSON).

Semistructured model, well-formed vs valid, IDREFS, XPath

Semistructured data model: a graph of nodes with labelled edges (the tag and attribute names). Leaves hold values, and everything hangs off one root. It's self-describing: the labels travel with the data, so missing or repeated fields are easy. IDREF links turn the tree into a general graph.

  • Well-formed: follows the syntax rules (one root, tags closed and properly nested, attribute values quoted). Valid: well-formed and matches its DTD, and every IDREF points to an existing ID.
  • IDREFS: a space-separated list of IDs, used for many-many links.

Bank schema (2023-24 S2): full trigger, tricky queries, output traces

The trigger must handle INSERT, UPDATE and DELETE, and work on many rows at once. Idea: turn every affected log row into (aid, delta) rows. New rows add their effect, old (deleted) rows subtract theirs. Then sum the deltas per account and apply them once. The GROUP BY matters because UPDATE…FROM with two matching rows for one account would apply only one of them.

CREATE TRIGGER trg_ActivityLog ON ActivityLog
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
  UPDATE A SET amount = A.amount + D.delta
  FROM Account A
  JOIN (SELECT aid, SUM(delta) AS delta FROM (
          SELECT aid1 AS aid, CASE WHEN optype='deposit' THEN amount ELSE -amount END AS delta
          FROM inserted                                         -- apply new rows to aid1
          UNION ALL SELECT aid2, amount FROM inserted WHERE optype='transfer'   -- + aid2
          UNION ALL SELECT aid1, CASE WHEN optype='deposit' THEN -amount ELSE amount END
          FROM deleted                                          -- undo old rows on aid1
          UNION ALL SELECT aid2, -amount FROM deleted WHERE optype='transfer'
        ) X GROUP BY aid) D
    ON A.aid = D.aid;
END;

Use UNION ALL, not UNION, so two identical deltas both count. If the question wants separate triggers, write one each for INSERT, DELETE and UPDATE.
