Refresher notes

Built around your Round 1 misses, most important first.

1 · Relational algebra (25 marks every paper)

The operators

  • σcond(R) selects rows · πattrs(R) projects columns and removes duplicates (sets)
  • × cross product · ⋈ natural join on shared names · ⋈cond theta join
  • ∪ ∩ − need the same schema · ρR1(a,b) renames (needed for self-joins)
  • γgroup attrs; AGG(x)→name(R) groups and aggregates (COUNT, SUM, MAX…)
  • ÷ division: R(A,B) ÷ S(B) gives the A values paired with every B in S

The 4 question patterns they keep asking

  • “…ALL X” → division. Divisor = the set of all X. Dividend = πanswer, X with nothing else left in.
    Without ÷: S − πA((S × Divisor) − R)
  • “at least N different X” → πwho, X first (remove repeats), then γwho; COUNT(X)→n, then σn≥N
  • “pairs who were together” → ρ two copies, join on the shared session columns, keep s1 < s2 (no self-pairs, no (b,a) duplicates)
  • “most / highest” → γ MAX joined back, or the “not dominated” trick: All − π(σL1.x < L2.x(L1 × L2)). Keeps ties.
Write it as named steps (T ← …, C ← …). Examiners give partial credit per step.

2 · SQL traps (you know SQL — these are the gotchas)

  • Inner join drops non-matching rows. No “count 0” row ever appears. LEFT JOIN + COUNT(*) gives 1. LEFT JOIN + COUNT(col) gives 0.
  • OR join conditions (from = id OR to = id): one row can match an account on both sides, so count every (row, row) pair by hand.
  • WHERE runs per row: cat='coffee' AND cat='tea' is always empty. Use two IN/EXISTS, or HAVING COUNT(DISTINCT cat)=2.
  • NULL: NOT IN and >= ALL return nothing if the subquery contains a NULL. NOT EXISTS and MAX are safe.
  • Ties: “return all” means >= ALL or = (SELECT MAX…), never TOP 1.
  • Division in SQL: double NOT EXISTS: “no X exists that this student didn't do”.
  • “No JOIN allowed”: nest IN / EXISTS subqueries instead.
  • WHERE vs HAVING: WHERE filters rows before grouping, and you can't use aggregates in it. HAVING filters groups after grouping.
  • NULL test: PromoCode IS NOT NULL, never <> NULL.
  • Dialect = SQL Server: GETDATE(), YEAR(d), FORMAT(d,'yyyy-MM'), TOP.

3 · Triggers (SQL Server)

CREATE TRIGGER name ON Table
AFTER INSERT, UPDATE, DELETE   -- or INSTEAD OF
AS
BEGIN
  -- inserted = new rows, deleted = old rows (tables!)
  IF EXISTS (...)
  BEGIN
    RAISERROR('msg', 16, 1);
    ROLLBACK TRANSACTION;
  END
END;
  • Fires once per statement. inserted/deleted can hold many rows, so write JOIN / GROUP BY code.
  • No NEW/OLD and no FOR EACH ROW. That's Oracle/Postgres.
  • Keeping a derived total correct needs INSERT + DELETE + UPDATE triggers. On UPDATE: add inserted, subtract deleted.
  • Constraint ways: key / attribute CHECK / tuple CHECK / assertion (multi-table, checked on every change) / trigger.

4 · FDs & normal forms

  • Closure X⁺: keep applying FDs whose LHS ⊆ current set.
  • Keys: attributes on no RHS are in every key; attributes only on RHS are in no key. Then grow from that core.
  • Prime = in some candidate key.
  • BCNF: every non-trivial X→Y has X a superkey.
  • 3NF: X is a superkey or every attribute of Y is prime.
  • BCNF ⊂ 3NF. Every BCNF relation is 3NF, so “BCNF but not 3NF” is impossible.
  • Minimal basis: split RHS → remove redundant FDs → shrink LHS (recheck).
  • 3NF synthesis: minimal basis → one relation per FD → add a key relation if none contains a key → drop subsets.
  • BCNF decomposition: pick violating X→Y, split into (X⁺) and (X ∪ rest), project the FDs onto each, repeat.
  • Lossless (binary): R1∩R2 → R1 or R1∩R2 → R2. Preserving: every FD checkable inside one piece (or derivable from the projected FDs).
  • Compare: BCNF has no FD redundancy and is lossless, but may lose FDs. 3NF is lossless and preserving, but may keep redundancy.
  • Adding an FD can never remove an implied FD.

5 · ER

  • Rectangle = entity set · oval = attribute (underlined = key) · diamond = relationship · triangle = ISA · double rectangle/diamond = weak.
  • Arrow points to the “one” side (many-one). Arrows on both sides = one-one.
  • ISA: ER-style (subclass = super key + own attrs) · OO-style (a full table per combination) · NULL-style (one table). The subclass key is the superclass key.
  • Weak entity: key = owner key + partial key.
  • Reverse engineering hints: several tables sharing the same key → ISA or a merged many-one. A composite key containing another entity's key → weak entity or relationship. A table that is all key columns referencing two entities → many-many relationship. A table with only a key → entity with no attributes.
  • Many-one relationships are usually folded into the “many” side's table.

6 · XML / index / views

  • DTD: none = exactly 1 · ? 0–1 · * 0+ · + 1+ · | choice · #PCDATA text.
  • <!ATTLIST E a CDATA #REQUIRED> · #IMPLIED optional · #FIXED "SGD" constant.
  • ID values: unique, start with a letter or _, no spaces (“B1”, not “1”). IDREF points to an ID.
  • XML needs exactly one root element. JSON arrays become repeated elements.
  • Structured vs unstructured vs semi-structured: fixed schema / no schema / self-describing tags.
  • Composite index: equality columns first, then the range/ORDER BY column. A tree index on x helps MAX(x), but not MAX(x·y). Low-selectivity filters (most rows match) gain little. Downsides: slower writes, extra space.
  • View = stored query, computed on use · materialized = stored result, fast to read, must be refreshed · temporary = session-only.
